# ReySo

Online store for ReySo, a women's clothing atelier. This is the existing static site ported to Next.js (App Router) + React + TypeScript, with the same look: the original stylesheets live in `src/styles` and the markup keeps the original class names.

```bash
npm install
cp .env.example .env   # set DATABASE_URL and PAYLOAD_SECRET
npm run migrate        # create the database tables
npm run seed           # load the starting catalogue (once, into an empty database)
npm run dev            # http://localhost:3000, admin panel at /admin
npm run build && npm start
```

The production build reads the catalogue from the database, so run `npm run migrate` before `npm run build`. The first visit to `/admin` creates the first admin account.

## Try it with Docker

`docker compose up --build` starts PostgreSQL and the store, runs migrations, loads the starting catalogue and builds the site (a few minutes on first start). Then open http://localhost:3000 and http://localhost:3000/admin. Data and uploads persist in Docker volumes; `docker compose down -v` wipes them. The compose file uses a fixed local secret: it is for trying the store, not for production.

## Admin panel

[Payload CMS](https://payloadcms.com) runs inside the same Next.js app at `/admin`, in Persian. Staff manage products, collections, images, lessons and the homepage's featured row there; any change re-renders the storefront. Uploaded images go to `MEDIA_DIR` (default `./media`), which must be persistent storage on the server.

- `src/payload.config.ts`, `src/payload/`: collections and the homepage global.
- `src/lib/catalog.ts`: what the storefront reads. Without `DATABASE_URL` it falls back to `src/data/seed-catalog.ts`.
- Schema changes: edit a collection, then `npm run payload -- migrate:create <name>` and commit the migration. Migrations also run automatically when the production server starts.

## Layout

- `src/app/(frontend)`: storefront routes; `src/app/(payload)`: admin panel and API (generated by Payload); `src/app/(store-api)`: the storefront's own API (SMS login and customer accounts, `src/lib/server`). Old `.html` addresses redirect to the new ones (`next.config.ts`, `src/proxy.ts`).
- `src/components`: site shell (`layout/`), product UI, shop, checkout, profile and page parts.
- `src/lib`: catalogue loader and types (`catalog.ts`, `products.ts`, `lessons.ts`), cart/wishlist/customer stores (localStorage, same keys as the old site), orders and order status, config.
- `src/styles`: the old site's CSS, unchanged apart from font paths.
- `public`: images, video, fonts and icons from the old site.

## Configuration

Settings and contact handles come from environment variables (see `.env.example`). Without a database (as on the GitHub Pages preview) the store keeps the old demo behaviour: orders stay in the visitor's browser and the support chat answers with a canned reply.

### SMS login and customer accounts

With a database, customers log in with an SMS code and their profile, addresses and wishlist are stored on the server (admin panel → مشتری‌ها). The browser keeps a copy in localStorage, synced by `src/lib/account.ts`; the session is a signed httpOnly cookie. Codes expire after 5 minutes, allow 5 tries, and are limited to one a minute and 5 an hour per number (20 an hour per IP).

Codes are sent with Kavenegar once `KAVENEGAR_API_KEY` and `KAVENEGAR_OTP_TEMPLATE` are set. Until then `SMS_DEMO=1` sends nothing and accepts `12345`; never set it in production. With neither, login is refused. The GitHub Pages preview has no server and keeps the old browser-only accounts with code `12345`.

### Orders and payment

With a database, orders are stored on the server (admin panel → سفارش‌ها). Prices, stock (sold-out sizes) and discount codes (admin panel → کدهای تخفیف) are checked on the server, so the browser can't change what a customer pays; if a price changed meanwhile, checkout shows the new total before paying. Each order gets a number like `RS261025-1234`, used for tracking. The admin dashboard shows today's sales, orders waiting to be handled and a sales report (7/30/90 days: daily sales, best sellers, sizes, colours, cities, discount codes, new vs returning customers).

Payment goes through Zarinpal once `ZARINPAL_MERCHANT_ID` is set (`ZARINPAL_SANDBOX=1` uses Zarinpal's test gateway). An order stays "awaiting payment" until Zarinpal confirms it; the customer can pay again from their profile. Until there is a merchant ID, `PAYMENT_DEMO=1` shows a fake bank page with pay/cancel buttons; never set it in production. With neither, orders are registered without online payment (marked "manual") for payment by card transfer.

## Preview on GitHub Pages

`.github/workflows/pages.yml` publishes a static preview to https://reysostyle.github.io/reyso-next/ on every push to `main` (enable it once under Settings → Pages → Source: GitHub Actions). The preview is a static export (`PAGES_BASE_PATH`) without the admin panel: it shows the built-in catalogue, old `.html` redirects don't apply there and the store runs in demo mode.
